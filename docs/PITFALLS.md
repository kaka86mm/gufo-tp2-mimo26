# Pitfalls

Everything that bit us, so it doesn't bite you. Each entry is numbered and other documents reference these numbers, so the order is fixed. Every one of these cost real time — most of them a production outage or a wrong measurement that survived for days.

**1. A symlinked cache directory fails the whole load and takes the pair down.**
*Symptom:* rank1 dies at startup with `Error loading model '<path>': TP disk cache directory: Not a directory`, the log shows `load_failed`, and rank0 immediately exits with `tp_pair_lost` — a directory-layout problem presenting as a transport failure. *Cause:* rank1's cache has to live on the data disk (28 GiB of snapshots against a nearly full root filesystem), so the natural fix is to point `--cache-disk` at a symlink — and the engine rejects it (an lstat/`O_NOFOLLOW`-style check). *Fix:* pass the real directory to the engine (`--cache-disk /mnt/data1t/cache-disk` on that host) and keep the symlink only as a human waypoint; the engine never sees the link. Nothing else about the path is checked.

**2. `--cache-disk-staging-bytes` is a cap, not a reservation.**
*Symptom:* the disk cache silently stops working above a size threshold. The directory stops growing, and requests report `usage.gufo.cache_miss_reason = "no_checkpoint"` — which reads like "this prefix has none" rather than "your snapshot was refused". We shipped 256 MiB and believed the disk cache worked; it was dead for every prefix over ~20K tokens. *Cause:* the flag bounds the RAM one queued snapshot may occupy and the RAM one disk read may occupy; a snapshot bigger than the cap is dropped with no error. A full 200K prefix snapshots ~2.6 GB per rank. *Fix:* size it to the largest snapshot you want to keep — 3 GiB here (`3221225472`). Watch `usage.gufo.cache_disk_queued_bytes` / `cache_disk_enqueue_ms` and count files in the directory, because nothing else will tell you.

**3. `--cache-ram-bytes` defaults to half of free RAM, capped at 32 GiB — pin it.**
*Symptom:* the L1 snapshot pool reserves far more than it can ever use. *Cause:* the default is evaluated at engine start, when "free RAM" is measured on a host whose page cache has not yet been filled by the weights; on a machine where 6 GB of headroom is the whole margin, that auto-size is a hazard, not a convenience. *Fix:* set it explicitly (1 GiB here). The pool only holds a couple of snapshots; the L2 disk cache is what actually carries continuation.

**4. A snapshot needs time to commit — the file appearing is not the snapshot being usable.**
*Symptom:* you watch the snapshot land, kill the engine seconds later, restart — and the prefix misses with `cache_miss_reason=no_checkpoint`; the snapshot file is pruned at the next start. *Cause:* write completion is not the commit/index step the next process needs. *Fix:* give a freshly written large snapshot ~2 minutes of idle before restarting. Measured both ways on the 193K prefix: killed seconds after the write → miss; written, 120 s idle, then restart → `cached_tokens=192910` and a 3.76 s restore. This is the difference between a 692 s cold prefill and 7.8 s.

**5. `no_checkpoint` can mean "never written", not "no checkpoint".**
*Symptom:* `cache_miss_reason=no_checkpoint` on a prefix the engine definitely continued, on a deployment whose other knobs are right. *Cause:* the reason code only reports that no usable checkpoint was found for the prefix; it does not distinguish "the prefix was never captured", "the snapshot was refused at staging" (#2), "the file was written but not committed" (#4), or "a checkpoint that should have landed never did". The last case is real: a capture path returned non-blocking and the caller erased the checkpoint unconditionally, so the previous snapshot was permanently lost — it showed up in 1 of 5 continuation attempts, each costing a 1,415-token re-prefill (4.9 s). After making the capture wait, three consecutive trials all reported `prefill_tokens=0` and cold prefill was unchanged (121.4 s). *Fix:* don't debug the prefix — check the staging cap and the commit window first, then look for a lost capture; the code tells you which prefix was considered, not why the snapshot is absent.

**6. `event=listening` is not readiness, and `/health` is not liveness.**
*Symptom:* the launcher prints `listening` and returns "success"; clients then get errors. Worse, rank0 answers `/health` with 200 for about a minute after its peer has died, so a restore can report success with rank1 gone. *Cause:* `event=listening` is emitted before the KV for a large context is allocated, and rank0's HTTP layer is up before (and while) its peer vanishes. *Fix:* readiness = `/health` returns 200 **and** the peer's engine process is alive on the other host — which is what `deploy/restore-prod.sh` waits for; a restore that reports failure is better than one that reports success with half a pair. Related default worth knowing while you are here: `--prefill-chunk 512` makes a 20K prefill run at 329 tok/s and stalls other sessions' decode for up to 2.3 s between tokens, where `64` gives 394 tok/s and 1.07 s stalls — we run 64. It is a concurrency knob, not a prefill-throughput knob.

**7. SIGTERM is not enough for an engine stuck in an uninterruptible GPU wait.**
*Symptom:* you stop the pair; the process is still there minutes later holding ~110 GB of GTT; the next load starts with ~12 GB free, the kernel OOMs it, the supervisor tries to restore again — a cascade. *Cause:* a rank in an uninterruptible GPU wait does not take SIGTERM, and its pinned memory is invisible to the OOM killer's process table, so nothing reclaims it. *Fix:* give SIGTERM a bounded wait, then escalate to SIGKILL (as `deploy/mimo-stop.sh` and `restore-prod.sh` do), verify the process is gone by binary path, and only then start the next load.

**8. Replacing the binary while a rank winds down fails with ETXTBSY — even though `pgrep` sees nothing.**
*Symptom:* `scp: dest open "<...>/gufo-mimo2-bin": Failure` (text file busy) during a deploy that pgrep says is safe. *Cause:* right after a SIGKILL the old process still maps the binary for a moment while it exits; the inode is busy but the process is invisible to `pgrep` (even its cmdline can read empty). *Fix:* copy to `$BIN.new` and `mv -f` — rename(2) is immune to the busy inode — and do it on both hosts. This cost ~4 minutes of production downtime; the supervisor's retry a few minutes later recovered the pair by itself.

**9. `flock` file descriptors are inherited by the engine.**
*Symptom:* after a restore, every later restore — including the supervisor's automatic one — fails with `another restore is already in flight`, with no restore running. *Cause:* the restore script takes the lock with `exec 9>/tmp/mimo-restore.lock`; every child it starts inherits fd 9, and the engine holds it for life, so the exclusive lock is never released. *Fix:* close the descriptor before launching long-lived children (`... 9>&- ...`), and verify with `ls -l /proc/<engine-pid>/fd` if you ever doubt it. `deploy/restore-prod.sh` carries the `9>&-` with a comment for exactly this reason.

**10. Two restores can want the same pair at once.**
*Symptom:* a manual restore and the supervisor's auto-restore overlap; each `pkill` kills the other's half; the pair ends up down. *Cause:* no mutual exclusion, and a shared guard marker that gets released by whoever exits first. *Fix:* take an exclusive `flock` for the whole restore, and only release the shared marker (`/tmp/mimo-no-supervise`) if this run created it — a script must not end an operator's test window it did not open. `deploy/restore-prod.sh` does both.

**11. A restore stuck in its readiness poll holds the lock indefinitely.**
*Symptom:* after a TB link flap, every restore says `another restore is already in flight`; a stray restore process is polling a rank that already `load_failed`. *Cause:* the poll's `ssh` calls had no connect timeout, so one dead link hangs the poll — and the poll still holds the `flock` (see #9 for the other way to keep the lock held). *Fix:* `-o BatchMode=yes -o ConnectTimeout=5` on every ssh in the restore path; if it has already happened, kill the stray process to recover. All ssh calls in `restore-prod.sh` now carry the timeout.

**12. The GTT guard threshold must sit above steady state, not near it.**
*Symptom:* the supervisor kills a healthy pair during a maintenance window. *Cause:* the guard was 112 GB while steady state was ~110 GB — a 2 GB margin, which a legitimate transient during load or deploy exceeds, so the guard fires on the wrong thing. *Fix:* put the limit above steady state and below what the host can survive — recalibrated to 118 GB. (The guard itself is mandatory: pinned GTT is invisible to the OOM killer, so polling `mem_info_gtt_used` and killing the engines is the only protection that works — see #7.)

**13. The supervisor's restore path must carry the same configuration as the launcher.**
*Symptom:* you change a flag (say `--context`) in the start script, and one supervisor tick later it silently reverts: the pair comes back with the old values. *Cause:* the restore path has its own copy of the launch parameters (`SESSIONS` / `CONTEXT` / RAM / staging / disk sizes), and the supervisor's automatic restore goes through it. *Fix:* one source for the parameter block, sourced by both the launcher and `restore-prod.sh`; if a value is overridden in the environment, the restore path must take it from there too, so an auto-restore reproduces the configuration the operator launched with. Changing a knob means changing both places until that is true.

**14. The two hosts can be on different clocks.**
*Symptom:* correlating logs across ranks shows rank1's timestamps eight hours "stale" — a request that clearly ran at 13:40 appears at 05:40 — and you conclude rank1 never started at all. *Cause:* one host is on UTC and the other on local time. *Fix:* set both hosts to the same timezone before doing cross-rank log forensics; if you cannot, convert every timestamp before believing an event order. This alone cost twenty minutes of misdiagnosis.

**15. HTTP rejects bodies above ~8 MB with 413 `payload_too_large`.**
*Symptom:* a large prompt returns HTTP 413 with error type `payload_too_large` before any inference happens. *Cause:* the serving layer caps the request body at ~8 MB. *Fix:* know the sizes — a 200K-token prompt body is only about 1 MB of JSON, so the cap is not the constraint for normal long-context work; it bites when prompts are inflated (attachments, base64, huge segment counts) or when a script expands a prompt past what it planned.

**16. Measuring concurrency: cohorts queue behind resident sessions.**
*Symptom:* a "mixed six-way" taken right after another six-way cohort reads **21 t/s**; taken right after the 58.7K cold prefill it reads **15.8 t/s**; the real figure is **55.0 t/s**. *Cause:* the previous cohort's sessions are still resident/ draining, so the new cohort queues — the client wall then measures queue time, not decode. *Fix:* drain between cohorts (the batteries sleep ~20 s and then confirm the six slots are free), and order the run so mixed cohorts are measured **before** the large prefills, never after. A concurrency number without a drain in front of it is not a decode number.

**17. The tokenizer's segment ratio: never predict prompt length from segment count.**
*Symptom:* a prompt intended as ~176K tokens is rejected with `context_length_exceeded`; a script predicts 54K tokens for 5,430 segments and the engine counts 58.7K. *Cause:* the `第%s章...` filler measures **11.736 tokens per segment** with 4-digit indices (the engine counted 492,914 tokens for 42,000 segments), but the ratio moves with the template and the index width — measured 11.7 to 16.3 across the templates used here. One early helper printed `approx_tokens = segments × 1.43`, an ~8× underestimate, which is how a 15,000-segment rung turned into a 243,910-token request. *Fix:* read `usage.prompt_tokens` from a real response (or the engine log) and calibrate the ratio per template; keep a margin under the window and treat the engine's `context_length_exceeded` rejection as the guardrail it is.
